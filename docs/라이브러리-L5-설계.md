# 라이브러리 L5 — 안드로이드 이식 설계안 (2026-11-25 · 결정 확정 · L5-0 ~ L5-6 끝)

웹 · 데스크톱의 라이브러리(L0 ~ L4, `Zenyth-web/docs/라이브러리-계획.md`)를 안드로이드로 옮기는 설계다. **같은 사이드카 ·
같은 색 표 · 같은 통계**를 지키고, 안드로이드에서 달라지는 세 가지 — 엔진이 *별도 프로세스의 실행 파일*이라는 점, 폴더가
*SAF 문서 URI*라는 점, 기기 메모리가 작다는 점 — 에 맞춰 구조를 고른다. 코드는 아직 바꾸지 않았다. 끝의 §9 결정이 나면 착수한다.

## 1. 전체 구조

```
            UI 프로세스 (dev.gomoku.rapfidroid)                          :library 프로세스            엔진 프로세스
┌──────────────────────────────────────────────────────┐   Messenger   ┌──────────────────────┐   stdin/out  ┌──────────┐
│ feature/library  LibraryScreen · Detail · Sheets     │ ───job────▶  │ LibraryJobService    │              │ Rapfi    │
│        ▲ StateFlow                                   │ ◀─progress── │  (포그라운드 dataSync)│              │ (자식)   │
│ data/library  LibraryRepository (항목 · 소스 · 작업줄)│ ◀─result──── │  scan · index ·      │              │          │
│   ├ sources: AppDirSource · SafTreeSource            │   (fd 로 전달)│  merge · split ·     │              │          │
│   ├ ManifestStore (zenyth-library.json, 정본)         │              │  writeBack · copy    │              │          │
│   ├ Reconciler (folderSync 포팅)                      │              └──────────────────────┘              │          │
│   └ LibraryAttachController (dbStore.switchTo 몫) ───── EngineRepository ── YXSETDATABASE <filesDir 경로> ─▶│          │
│ domain/library/yxdb  코덱 · 색인 · 병합 · 분리 (순수 Kotlin, JVM 시험) ← 두 프로세스가 같은 코드          └──────────┘
└──────────────────────────────────────────────────────┘
```

- **세 프로세스, 각자 한 가지**: UI 는 화면과 메타데이터, `:library` 는 무거운 바이트 처리, 엔진은 탐색과 붙은 DB.
- **엔진은 언제나 `filesDir` 아래 ASCII 경로만 본다** — 앱 저장소 파일은 그대로, SAF 파일은 스테이징 사본(§3.3). 한글 경로를
  `YXSETDATABASE` 로 넘기는 위험(웹 L4 의 «확인하지 못한 것»)이 안드로이드에선 생기지 않는다.
- 패키지: `domain/library/yxdb/*`(코덱, 안드로이드 의존 없음) · `domain/library/*`(항목 모델 · 사이드카 코덱 · 파일 이름 · 커버 열쇠) ·
  `data/library/*`(소스 · 저장소 · 작업 클라이언트 · 붙이기) · `data/library/job/*`(서비스) · `feature/library/*` ·
  `core/designsystem/cover/*`(색 표 · `DbCover`).

## 2. 코덱 · 워커

### 2.1 코덱 — 웹을 바이트 단위로 옮긴다 (`domain/library/yxdb`)

| 파일 | 웹 원본 | 안드로이드에서 다르게 하는 것 |
|---|---|---|
| `Lz4Frame.kt` | `lz4frame.ts` | 해제: 연결 블록 64KB 창 · BD 64K ~ 4M · 머리 체크섬 · 이어진 프레임. **`ByteArray` 하나를 창+블록 버퍼로 재사용**, 레코드마다 객체 할당 0. 압축: FLG `0x64` · 4MB 독립 블록 · 내용 xxh32 · 큰 쪽은 raw — 같은 greedy fast(`imul(v, 2654435761) ushr 16`) |
| `Xxh32.kt` · `Fnv1a64.kt` | 같은 이름 | 벡터 그대로 시험(`""`→`02cc5d05`, `"abc"`→`32d153ff` / `""`→`cbf29ce484222325`, `"a"`→`af63dc4c8601ec8c`, `"foobar"`→`85944171f73967e8`) |
| `YxdbReader.kt` · `YxdbCursor.kt` · `YxdbWriter.kt` | `yxdbfile.ts` · `yxdbmerge.ts` | 입력은 `ReadableByteChannel`(앱 파일 = `FileChannel`, SAF = `ParcelFileDescriptor` 의 채널). 256KB 직접 읽기. 레코드 콜백은 `(buf, keyOff, keyLen, valOff, valLen)` 오프셋만 — 웹의 «`subarray()` 는 할당» 교훈 |
| `YxdbKey.kt` | `compareYxdbKeys` | rule · w · h · 돌 수 · 돌 바이트 · 둘 차례 순서 |
| `YxdbIndex.kt` | `yxdbindex.ts` | 슬롯 `IntArray [hi, lo, info]` + `parent IntArray` + 블룸 `ByteArray`. **Zobrist 표는 웹 것을 그대로**(splitmix64, `s0 = 0x5a454e595448`, `colour*1024 + (x<<5 \| y)`) — 기존 `domain/rif/Zobrist.kt`(팩 시드 `0x2545F4914F6CDD1D`, 칸 번호 `y*size+x`)와 섞지 않는다. 결과가 웹과 같아야 사이드카의 통계가 기기 사이에 그대로 믿을 만하다 |
| `YxdbMerge.kt` · `YxdbSplit.kt` | 같은 이름 | 정책 · 주석 이어 붙이기(64KB) · `UnderTest` 그대로. 순서가 아닌 입력의 32MB 정렬 묶음은 `Blob` 대신 **`cacheDir/library/spill/<job>/`** 파일 |
| 분류 | `opening26.classify` | 기존 `core/model/Opening26.classify` 를 쓴다(자체 변환 순서지만 결과는 같아야 함 — 웹이 뽑은 3돌 전수 골든으로 고정) |

**성능 방침(ART)** — 웹 L0 의 교훈을 그대로 적용하고 안드로이드 몫을 더한다.

- 해시 루프는 `Int`/`Long` 원시 값만(박싱 금지), `inline` 없이도 JIT · AOT 가 펴도록 짧은 루프. 이웃 키 접두 해시 재사용, 부모 후보를
  모아 조회해 캐시 미스를 겹치기, 없는 후보는 블룸으로 거르기 — 2차 통과가 시간의 대부분(표본 기준 웹 44s 중 41 ~ 49s).
- 해제 · 해시는 **스레드 하나**(엔진과 CPU 를 다투지 않게). 큰 코어 고정은 하지 않는다.
- JNI(LZ4 C) 는 처음엔 넣지 않는다 — 시간을 정하는 것은 무작위 조회(메모리 지연)라 C 로 바꿔도 이득이 작고, Gradle 에 NDK 빌드가
  새로 생긴다. L5-0 측정에서 해제가 40% 를 넘으면 그때 다시 본다.
- 예상(측정 전 추정, Galaxy A16 A76 1코어 ≈ Celeron N4500 의 2배): 79MB 표본 통계 3 ~ 5s, 색인 25 ~ 45s. **L5-0 에서 실측해 이 표를 갈아 쓴다.**

### 2.2 작업 프로세스 `:library` — 웹 전용 워커의 안드로이드판

`<service android:name=".data.library.job.LibraryJobService" android:process=":library" android:foregroundServiceType="dataSync">`

왜 따로 프로세스인가:

1. **힙 한도가 프로세스마다**다. ART 의 `allocateDirect` 도 자바 힙(non-movable)에서 나오므로 «힙 밖에 두기»가 안 된다. 색인 137MB 를
   UI 프로세스에 올리면 화면 · 보드 비트맵과 같은 한도(흔히 256MB)를 나눠 쓴다. 따로 띄우면 `:library` 는 한도를 혼자 쓴다 — `largeHeap` 불필요.
2. **즉시 취소** = 웹의 `terminate()`. 협조 플래그(`AtomicBoolean`, 스트림 조각마다 확인) → 1.5초 안에 멈추지 않으면(정렬 같은 동기 구간)
   UI 가 `Process.killProcess(pid)`. 임시 파일은 다음 작업 시작 · 앱 기동 때 쓸어 낸다.
3. **OOM · LMK 격리** — 색인이 터지거나 저메모리로 죽어도 보드 · 엔진은 그대로. UI 는 `binderDied` 로 알아채 «주형 통계는 이 기기에서 생략»으로 낮춘다.

비용과 대응: `ZenythApp.onCreate` 가 프로세스마다 돈다 → `Application.getProcessName()` 이 `:library` 면 Hilt 그래프 · 엔진 · 테마 초기화를
건너뛰는 분기 하나. 서비스는 Hilt 없이 코덱만 부른다.

**메시지(웹 `job` · `jobProgress` · `result` 와 같은 모양)** — `Messenger` + `Bundle`, 바이트는 절대 넘기지 않는다. 입력 · 출력은
`ParcelFileDescriptor`(앱 파일은 `open(File)`, SAF 는 `contentResolver.openFileDescriptor`) — UI 프로세스가 열어 넘기므로 `:library` 는 SAF 권한이 없어도 된다.

| 작업 | 입력 | 결과 |
|---|---|---|
| `scan`(통계 + 색인) | fd, 기대 정체, 색인 예산 | `DbStats` JSON, `indexSkipped` · `openingsSkipped` |
| `mergeCount` / `mergeWrite` | fd 여럿 · 순위 · 정책 | 합계 · 겹침 · 값 다름 / 출력 fd 에 쓰고 **다시 읽어 수 대조** 뒤 성공 |
| `splitCount` / `splitWrite` | fd · 기준 · (판 국면) | 기준별 개수 / 출력 fd 여럿 |
| `copy`(스테이징 · 되쓰기 · 소스 간 복사) | fd → fd | 바이트 수 · 끝 4KB 지문 (복사하며 계산 — 다시 읽지 않는다) |

- 진행 소식은 10Hz 로 묶는다. 작업 줄은 하나씩(`LibraryRepository` 의 `Channel` 큐).
- 포그라운드 알림: 진행 막대 + [취소]. Android 15 의 dataSync 시간 한도는 `onTimeout` 에서 취소(`PackBuildService` 선례). 알림 권한이 없어도 작업은 돈다.
- **엔진과 나눠 쓰기(모바일 몫)**: 통계 자동 세기는 낮은 우선(`THREAD_PRIORITY_BACKGROUND`), 엔진이 `Thinking` 이거나 `ThermalMonitor` 가
  심각 이상이면 **다음 조각에서 쉰다**(취소가 아니라 일시 정지). 사용자가 누른 병합 · 분리는 쉬지 않는다.

### 2.3 메모리 관문

```
budget = min( totalMem / 16,                       // 웹 deviceMemory/16 과 같은 눈금 (4GB → 256MB)
              :library 의 Runtime.maxMemory() × 0.6, // 힙 한도 (서비스가 첫 메시지 답에 실어 보낸다)
              (availMem − threshold) / 2 )          // 지금 엔진이 해시 · DB 를 쥐고 있는 몫
색인 = indexBytesEstimate(n) ≤ budget 일 때만        // 16n + 4·2^bucketBits + 2^bloomBits/8 + 4MiB (웹 식 그대로)
```

- 넘으면 색인 없이 기본 통계만(O(1) 메모리) — 상세는 늘 [빈 판에서 열기] [편집기로] 로 막힘이 없다(조건 ③).
- 작업 중 `onTrimMemory(RUNNING_CRITICAL)` 이면 색인을 스스로 버리고 기본 통계만 돌려준다.
- **두 단계 보고**: 1차 통과(통계)가 끝나는 즉시 카드에 국면 수 · 규칙을 띄우고, 색인(주형 · 뿌리)은 이어서 채운다 — 큰 DB 도 첫 정보가 몇 초 안에.

## 3. 소스 — 앱 저장소 · SAF 폴더

### 3.1 인터페이스 (웹 `source.ts` 와 같은 동사)

```kotlin
interface LibrarySource {
    val id: String; val kind: Kind            // APP | SAF
    suspend fun list(): List<FileStat>         // name · size · mtime(ms) — 한 번의 질의로
    suspend fun openRead(name: String): ParcelFileDescriptor
    suspend fun fingerprint(name: String, stat: FileStat): Fingerprint   // 끝 4KB 만 seek 해서
    suspend fun writeAtomic(name: String, job: suspend (ParcelFileDescriptor) -> Unit): FileStat
    suspend fun rename(from: String, to: String): String                   // 실제로 붙은 이름을 돌려준다
    suspend fun trash(name: String): String                                // 휴지통 속 이름
    suspend fun restore(trashName: String, name: String): String
    suspend fun purge(trashName: String)
    suspend fun readManifest(): Manifest; suspend fun writeManifest(m: Manifest)
    val access: StateFlow<Access>                                          // GRANTED | LOST
}
```

### 3.2 `AppDirSource` — 기본 «이 기기»

- 폴더 `filesDir/library/`, 파일은 **`<uuid>.db`**(웹 브라우저 소스의 `lib/<id>` 와 같은 태도 — 보이지 않는 저장소라 파일 이름에 뜻이 없다).
  같은 `zenyth-library.json` 을 이 폴더에도 둔다 → **사이드카 · 맞추기 코드 한 벌**로 두 소스를 다룬다(웹은 Dexie 와 사이드카 두 벌).
- 엔진이 `YXSETDATABASE /data/user/0/…/files/library/<uuid>.db` 로 **복사 없이** 연다.
- 원자 쓰기: 같은 폴더 `.<uuid>.db.zenyth-tmp` → `FileDescriptor.sync()` → 다시 읽어 수 대조 → `File.renameTo`(같은 파일 시스템, POSIX 원자).
- 휴지통: `filesDir/library/.zenyth-trash/<ms>-<name>`(웹 FSA 와 같은 이름 꼴) + 항목 `trashedAt`, 기동 때 30일 정리.
- **이관(첫 기동, 한 번)**: 엔진을 띄우기 전에 `filesDir/engine/rapfi.db` · `.journal` · 번호 백업(DB1 `makeBackupFilePath` 꼴 — 정확한 꼴은 L5-0 에서 확인)을
  `library/<uuid>.db*` 로 `renameTo`(복사 없음) → 항목 «내 DB»(커버 «일식», 정체 계산) → 붙을 항목으로. 실패하면 아무것도 옮기지 않고 다음 기동에
  다시(이관 표지 `library/.migrated`). 본 파일 없는 저널은 버린다(웹 L1 과 같다).
- 백업 규칙(`data_extraction_rules.xml`): 지금은 `rapfi.db` 가 클라우드 백업에 들어간다 → §9-7 결정.

### 3.3 `SafTreeSource` — 폴더 (`OpenDocumentTree`)

**권한**
- 고른 즉시 `takePersistableUriPermission(READ | WRITE)`, 줄은 DataStore `library_sources`(트리 URI · 표시 이름). 기동 때
  `persistedUriPermissions` 와 대조해 빠졌으면 `access = LOST` → 칩 줄 아래 «폴더 다시 허용»(`EXTRA_INITIAL_URI` 로 같은 폴더를 연 피커).
- 영구 권한 한도(128 · API 30+ 512)를 넘기지 않게 «라이브러리에서 빼기»는 `releasePersistableUriPermission` 까지.
- Android 11+ 피커는 저장소 루트 · `Download` 루트를 막는다 → 안내 한 줄 «`Documents/Zenyth` 처럼 폴더 하나를 만들어 고르세요».

**속도 (SAF 는 호출 하나가 바인더 왕복)**
- 목록은 `buildChildDocumentsUriUsingTree` **질의 한 번**에 `_ID · DISPLAY_NAME · SIZE · LAST_MODIFIED · MIME · FLAGS` 를 다 받는다. 이름 → 문서 id
  캐시를 들고 있고, 맞추기 한 번에 질의는 목록 1 + 휴지통 1 + 사이드카 읽기 1.
- 지문은 `openFileDescriptor("r")` 의 채널을 `size − 4096` 으로 `position` → 4KB 만 읽는다(seek 이 안 되는 공급자는 스트림 건너뛰기로 대체).
- 큰 읽기 · 쓰기는 `FileChannel` 256KB, 복사는 `transferTo`.
- 로컬 공급자(내장 저장소 · SD · USB OTG)를 기준으로 하고, 클라우드 공급자(드라이브 등)는 고를 수는 있되 «열 때마다 내려받을 수 있음» 한 줄.

**원자 교체 — SAF 에는 «덮어쓰는 rename» 이 없다**

`ExternalStorageProvider.renameDocument` 는 이름이 겹치면 실패하지 않고 ` (1)` 을 붙인 **다른 이름**으로 바꾼다. 그래서 늘 결과 이름을 다시 읽고,
교체는 세 걸음 + 복구 표로 한다.

```
1. createDocument("<name>.zenyth-tmp")  → 끝까지 쓰기 → sync → 다시 읽어 레코드 수 대조
2. rename  <name>            → <name>.zenyth-old       (본 파일이 있을 때만)
3. rename  <name>.zenyth-tmp → <name>                  (돌려받은 이름이 <name> 인지 확인)
4. delete  <name>.zenyth-old
```

| 다음 맞추기에서 본 것 | 뜻 | 처리 |
|---|---|---|
| `<name>` 없음, `.zenyth-old` 있음, `.zenyth-tmp` 있음 | 2와 3 사이에서 끊김 | tmp 를 다시 읽어 머리 수 = 레코드 수면 3을 마저, 아니면 old 를 되돌림 |
| `<name>` 없음, `.zenyth-old` 만 | 3 실패 | old → `<name>` |
| `<name>` 있음 + `.zenyth-old` | 4 전 끊김 | old 지우기 |
| `.zenyth-tmp` 만 | 1 도중 끊김 | 지우기 |

- 이 이름들은 `.db` 로 끝나지 않아 웹 `isDbFileName` · 데스크톱 `lib_list` 가 이미 무시한다(호환 문제 없음). 사이드카도 같은 세 걸음으로 쓴다.
- **휴지통** = 웹 FSA 와 **같은 자리** `.zenyth-trash/<ms>-<name>`(짝 파일은 같은 토큰 + 접미) — PC 에서 연 웹 · 데스크톱이 같은 휴지통을 본다.
  옮기기는 `DocumentsContract.moveDocument`(트리 안, `FLAG_SUPPORTS_MOVE`), 안 되는 공급자는 작업 프로세스의 복사 → 지우기(진행 막대).
  30일 정리는 맞추기 때 `<ms>` 접두로.
- **이름 바꾸기(파일 이름 같이)**: `fileNameFor`(웹 규칙 그대로 — NFC · 금지 문자 · 끝 점/공백 · 예약 이름 · 255바이트 · ` (2)`)로 이름을 정하고,
  목록에서 겹침을 먼저 본 뒤 `renameDocument`. 짝 파일(`^\.(journal|bak\d*|backup\d*|\d+)$`)도 함께, 반쯤 하다 실패하면 되돌린다. 안드로이드 외부 저장소는
  대소문자를 가리지 않으므로 대소문자만 다르면 `.zenyth-rename` 을 거쳐 두 번(웹과 같다). 공급자가 거절하면 제목만 바꾸고 `fileRenamePending`.
- **붙은 SAF 항목의 이름 바꾸기는 엔진을 건드리지 않는다** — 엔진은 스테이징 사본을 쥐고 있으므로(아래) 문서 이름만 바꾸고 되쓰기 때 새 이름을 쓴다.
  데스크톱의 «떼기 → 옮기기 → 다시 붙이기»가 필요 없다.

**스테이징 — SAF 파일을 엔진에 붙이는 법**

```
붙이기   : SAF <name>.db ──copy(작업 프로세스, 지문 동시 계산)──▶ filesDir/library/staging/<id>.db
            (스테이징이 이미 있고 base 지문 = 지금 SAF 지문이면 복사 생략)
            → YXSETDATABASE <스테이징 경로>
쓰는 동안 : 엔진이 스테이징에 저장(저널 · DB1 원자 저장 그대로) → 항목에 dirty
되쓰기   : YXCOMPACTDATABASE → «Saved database file» → 스테이징을 SAF 로 원자 교체 → base 지문 갱신 · dirty 해제
```

- 스테이징 표지 `staging/<id>.json` = `{ base: SAF 지문, dirty, sourceId, name }` — 앱이 죽어도 남아 다음 기동에 이어서 되쓴다.
- **되쓰기 시점**: (a) 다른 DB 로 바꿀 때 (b) 떼거나 엔진을 끌 때 (c) 앱이 백그라운드로 갈 때(`ProcessLifecycleOwner` ON_STOP) dirty 면 — 짧은 dataSync
  포그라운드로 마무리. (a)는 바꿔 붙이기를 기다리게 하지 않는다(스테이징이 항목마다라 되쓰기는 작업 줄에서 뒤따른다).
- **충돌**: 되쓰기 직전 SAF 지문이 base 와 다르면(그새 PC 가 고침) 덮어쓰지 않고 `<name> (이 기기).db` 로 따로 놓고 한 줄 알림. 잃는 쪽이 없다.
- 붙어 있는 동안 SAF 쪽 파일은 마지막 되쓰기 시점의 «접힌 한 벌» — 웹의 **쉬는 파일 불변식**이 폴더에서도 지켜진다(Yixin Board · PC 가 언제 열어도 온전한 파일).
- 비용: 100MB 복사 ≈ 1 ~ 2초(UFS). 붙일 때 한 번, 되쓸 때 한 번.

## 4. 사이드카 · 맞추기 — 호환이 가장 중요한 곳

- 모양: `{ "version": 1, "app": "zenyth", "entries": [...] }`, 들여쓰기 한 칸 + 끝 줄바꿈, 항목은 `createdAt` → `id` 순. 항목 칸은 웹 `LibraryEntry` 그대로
  (`id` UUID v4 · `file` · `title` · `cover {mode, opening?, seed}` · `fingerprint {size, mtime, tail}` · `stats?` · `createdAt` · `updatedAt` · `lastOpenedAt?` ·
  `trashedAt?` · `trashFile?` · `missingSince?` · `fileRenamePending?`).
- **모르는 칸을 지운다면 호환이 깨진다** → 항목마다 원래 `JsonObject` 를 들고 아는 칸만 덮어 쓴다(웹이 나중에 칸을 더해도 안드로이드가 지우지 않는다).
  최상위의 모르는 칸도 같다. 읽기 규칙은 웹 `parseManifest` 와 같게(필수 칸이 없는 항목은 버리고, 깨진 JSON 은 빈 목록 — 단 **깨진 사이드카는
  덮어쓰기 전에 `zenyth-library.json.broken-<ms>` 로 남긴다**).
- `tail` = 끝 4096바이트(작으면 전부)의 FNV-1a 64, 소문자 16자리 hex. `mtime` 은 ms — SAF 는 `COLUMN_LAST_MODIFIED`, 앱 파일은 `lastModified()`.
  안드로이드가 쓴 뒤에는 **공급자가 돌려준 mtime** 을 적어 PC 쪽 맞추기가 다시 재지 않게 한다.
- `stats` 도 사이드카에 들어간다 → 안드로이드가 센 통계를 웹이 그대로 믿는다. 그래서 §8 의 **교차 골든**(같은 합성 DB → 웹 · 안드로이드 `DbStats` 가 같다)이 필수다.
- 맞추기(`Reconciler.kt`)는 웹 `folderSync.reconcile` 를 한 줄씩 옮긴다 — 이름 열쇠 `NFC + lowercase`, 크기 · 시각이 같으면 그대로 / 다르면 지문 다시 /
  꼬리가 다르면 통계 버림 → 짝 잃은 항목은 같은 크기 파일 중 지문으로 다시 짝 → 그래도 없으면 `missingSince`(30일 뒤 버림, 파일 없이 만든 새 DB 는 예외) →
  남은 `.db` 는 «자동» 커버 새 항목 → 다른 소스와 겹친 id 는 새 UUID. 사이드카 쓰기는 소스마다 한 줄(`Mutex`).

## 5. 엔진 DB 전환 (`LibraryAttachController`)

로컬 엔진만 대상이다(원격은 §9-5). 웹 `dbStore.switchTo` 와 같은 순서:

```
switchTo(id):
 0. 대상이 이미 붙어 있으면 고르기만
 1. 지금 DB 가 LOADED · 쓰기 가능이면 YXCOMPACTDATABASE → DbFileEvent(saving 끝) 대기 (크기에 비례한 시한)
    · 실패하면 바꾸지 않는다
 2. INFO usedatabase 0  (DatabaseAttachGuard 상태도 되돌린다)
 3. 대상 경로 준비 — APP: library/<uuid>.db  /  SAF: 스테이징(§3.3)
 4. YXSETDATABASE <절대 경로>  → yxquerydatabaseone 안부 · DbFileEvent(load 끝) 로 붙었는지 확인 (적재 중엔 이름 붙은 진행 막대)
 5. 이전 항목이 SAF dirty 면 되쓰기를 작업 줄에 넣는다
 6. 다음 기동을 위해: MobileEngineConfig.render 가 config.toml 의 url 을 붙을 항목의 경로로 굽는다
    (기동 직후엔 지금처럼 INFO usedatabase 1 로 붙고, 실행 중 바꾸기만 YXSETDATABASE)
```

- 새로 감쌀 명령: `YXCOMPACTDATABASE`(`DatabaseCommand.kt`). `DatabaseRepositoryImpl` 의 `LoadState` · 저장 중복 방지 · 자동 저장은 그대로 쓰고,
  자동 저장이 «붙은 항목의 파일»에 쓰였다는 것만 `LibraryRepository.recordSaved` 로 알린다(본 파일이 바뀌면 지문 갈고 통계 버림 — 저널만이면 그대로).
- DB 를 열어 판으로: 웹 결정(2026-11-23) 그대로 — 가장 큰 뿌리(기록이 시작되는 국면)로 옮기고, 두던 판은 기존 «두던 판으로 돌아가기 · 버리기»(`from = library`).
- 작업 중 입력 항목은 «작업 중» 배지로 이름 바꾸기 · 지우기만 잠그고, 열람 · 붙이기 · 다른 탭은 그대로(웹 §4). 붙은 DB 가 병합 · 분리에 끼면 먼저 1번(접어 저장).
- 사전 확인(L5-0): 우리 엔진 빌드에서 `YXSETDATABASE` 가 `enable_by_default=false` 인 채로도 바로 적재하는지, 그 뒤 `usedatabase 1` 을 보내면 두 번 여는지
  (웹 L4 는 «보내지 말 것»으로 정리) — 호스트 빌드 또는 `test-yixin/engine.exe` 로 본다.

  돌 반지름 = 간격 × 0.44, 테두리 1.2, 세 돌 화면 좌표 상자 가운데를 (50, 50) 으로. 일식 = `seed%8 × 45°` 방향, 틈 `[17,19,21][seed/8 % 3]`, 진주 r23 · 후광 r25.25 · 원반 r20.75.
  `coverKeyOf`(자동 = 최빈 주형, 같으면 작은 번호 / 그 밖 `seed` 짝홀 → e0 · e1), 커버 시트의 일식 다시 누르기 `seed = (seed+1) % 48`.
- 그림은 `drawWithCache` 로 경로를 한 번 만들고 격자 스크롤 중 다시 만들지 않는다. 그림 저장(비트맵 캐시)은 하지 않는다 — 웹처럼 «주형 번호 · seed 만».

### 6.5 시트 (`ZenythSheet`, 모서리 28)

- **이름**: 글 칸 + «파일 이름도 같이 바꾸기»(폴더 소스 기본 켬, 앱 저장소는 숨김) + 거른 이름 미리 보기.
- **커버**: 실시간 미리 보기 · [자동] [일식] · 直 13 / 間 13 미니 커버 격자(7열) · 체크 원.

## 9. 결정 (사용자, 2026-11-24)

**아래 11개 모두 «제안(권장)» 열대로 확정.** 덧붙인 조건 둘:

- 되쓰기는 **실제로 바뀌었을 때(dirty)만** — 붙인 뒤 엔진의 저장 완료(`DbFileEvent` saving 끝)가 있었고, 접어 저장한 스테이징의 지문이 base 와
  다를 때만 SAF 로 쓴다. 바뀐 것이 없으면 접기 · 복사 둘 다 하지 않는다.
- 백그라운드로 갈 때의 큰 쓰기가 OS 에 잘리지 않게 — 아래 «안전한 백그라운드 되쓰기».
- 취향이 크게 갈리는 것은 구현 중 그 순간에 짧게 묻는다.

**안전한 백그라운드 되쓰기.** Android 12+ 는 백그라운드에서 포그라운드 서비스를 새로 띄우지 못하게 막는다. 그런데 스테이징이 dirty 라는 것은
로컬 엔진이 떠 있었다는 뜻이고, 그동안 `EngineService` 가 이미 포그라운드다(`specialUse` / `dataSync`). 그래서:

1. `ProcessLifecycleOwner` ON_STOP → dirty 면 `EngineService` 에 «되쓰기 끝날 때까지 내려가지 마» 표지를 걸고(알림 문구 «DB 저장 중»), 그 안에서
   `YXCOMPACTDATABASE` → `:library` 에 복사 작업을 bind 로 맡긴다(포그라운드 서비스를 가진 프로세스가 bind 한 프로세스는 같은 우선순위를 받는다).
2. 되쓰기는 §3.3 의 세 걸음 원자 교체라 **어디서 끊겨도 SAF 쪽은 옛 파일이거나 새 파일** — 중간 상태가 없다. 끊기면 스테이징 표지(`dirty`)가
   남아 다음 기동(포그라운드)에 이어서 한다.
3. 엔진이 이미 내려가 있는데 dirty 가 남은 경우(강제 종료 등)는 백그라운드에서 새로 서비스를 띄우지 않고 다음 기동 때 처리한다.
4. 작업 중 `onTimeout`(Android 15 dataSync 한도) · 저메모리 종료도 2번과 같다 — 잃는 것 없이 다음에 이어 간다.

## 10. 웹 쪽에 돌려줄 것 (L5 와 함께 작게)

- **(L5-0 에서 찾음 → 세 앱 함께 고침, 2026-11-24) 엔진 번호 백업의 이름**: DB1 의 `makeBackupFilePath` 는 `<줄기>_bak<N><확장자>` — `연구.db` 의
  백업은 `연구_bak1.db` · `연구_bak2.db`(`num_backups_on_save = 2`). 예전 웹 · 데스크톱은 이것을 새 DB 로 잡고 짝으로 보지 않았다. 이제 규칙은 하나:
  - 짝 꼬리 `companionSuffix(base, name)` 가 `.journal` · `.bak*` · `.<숫자>` 에 더해 **`_bak\d+\.db`(줄기 기준, 대소문자 무시)** 를 돌려준다. 붙일 때는
    `withTail(base, tail)` — `_` 로 시작하면 줄기에(`b.db` + `_bak1.db` → `b_bak1.db`), 아니면 뒤에.
  - 폴더 맞추기는 **본 파일(`<줄기>.db`)이 같은 폴더에 있을 때만** `<줄기>_bak<N>.db` 를 항목에서 뺀다(`isEngineBackup`). 본 파일 없는 백업은 그대로 DB —
    사용자가 되살릴 수 있게. 예전에 항목이 된 백업은 «없어짐»으로 숨었다가 30일 뒤 버려진다.
  - 이름 바꾸기 · 휴지통 · 되돌리기 · 아주 지우기가 짝을 함께 옮긴다. 웹 `source.ts` · `fsaSource.ts` · `folderSync.ts`, 데스크톱 `library.rs`
    (`companion_suffix` · `companion_name`), 안드로이드 소스(L5-2)가 같은 규칙.
- **(L5-0 에서 찾음 → 두 앱 함께 고침, 2026-11-24) 색인 해시의 규칙 · 판 소금**: 예전 Zobrist 는 돌만 보아 같은 돌의 렌주 · 표준 · 자유 국면이 한
  국면으로 합쳐졌다(교차 골든 `mixed`: 주형 합 433 ≠ 렌주 + 표준 442, 뿌리 하나 475). 이제 해시는 0 이 아니라 `ruleSalt(rule, w)`(splitmix64 한 걸음,
  씨 `"RULE" << 16 | rule << 8 | w`)에서 시작한다 — 8 변환에 같은 값이라 정규화 · 부모 해시는 그대로 맞는다. 고정값 `ruleSalt(2, 15) = f8e1fdffa82a22c5`
  를 두 앱 시험이 대조. 새 골든: 주형 합 442, 뿌리 넷(렌주 414 · 표준 28 · 자유 15 27 · 자유 20 16).
  - `DbStats.indexVersion = 2`(`INDEX_VERSION`). 옛 통계(칸 없음 = 1)는 **규칙 · 판이 둘 이상일 때만** 다시 센다(`statsCurrent` / Kotlin `DbStats.current`) —
    한 규칙만 든 DB 는 두 판의 결과가 같아 버릴 까닭이 없다. 웹은 통계 줄(`libraryStore.pump`)이 그런 항목을 집어 다시 세고 사이드카에 쓴다.
- **데스크톱 `YXSETDATABASE` 앞 `usedatabase 0`**: 엔진이 새 저장소를 만든 뒤 옛 것을 놓으므로, 웹 `dbStore.attachFolderFile` 도 이제 먼저 옛 저장소를
  놓는다(엔진 설정이 미리 연 DB 와 새 DB 가 한꺼번에 메모리에 들지 않게). 바꿔 붙이기에선 접어 저장 단계의 것과 두 번 가지만 두 번째는 할 일이 없다.

- `.zenyth-old` · `.zenyth-tmp` · `.zenyth-rename` 는 이미 무시되지만, 웹 `fsaSource.list` 도 데스크톱처럼 명시적으로 걸러 두면 안전하다.

**바꿔 붙이기 순서**(§5): 같은 항목이면 끝 → 대상 경로(앱 = 그대로, SAF = 스테이징) → 엔진이 DB 를 쥐고 있으면 탐색을 멈추고(`awaitIdle` — 탐색 중엔 정지 말고는 다 버린다)
접어 저장(불러온 · 쓰기 가능한 DB 만, 진행 중 저장이 있으면 끝을 기다림) — **실패하면 아무것도 바꾸지 않는다** → `INFO usedatabase 0` → `YXSETDATABASE <경로>` + `ABOUT`
(명령은 순서대로 돌고 적재는 동기라 `ABOUT` 답 = 붙음; 실패면 옛 것을 다시 붙이고 «실패») → 판 다시 질의 → 기록 → 남겨진 SAF 항목이 dirty 면 되쓰기를 뒤에 건다.
엔진이 DB 를 쥐고 있지 않으면(꺼짐 · 연결 없음) 기록만 바뀐다.

**되쓰기**(§3.3 · §9): 저장 끝(`DATABASE SAVE DONE` 또는 `Saved database file`)마다 붙은 SAF 사본의 본 파일 · 저널 지문을 `base` 와 견줘 다르면 `dirty`.
dirty 일 때만 — 엔진이 쥔 사본은 접어 저장한 뒤 — 폴더 파일이 `base` 그대로면 원자 교체(세 걸음)로 덮고, 아니면 `<줄기> (이 기기).db` 로 따로 놓고 새 항목을 사이드카에 더한다.
덮은 뒤 사이드카 항목의 지문을 공급자가 돌려준 mtime 으로 갈고 꼬리가 바뀌면 통계를 버린다. 복사하는 동안 새 저장이 끝났으면 dirty 를 그대로 둔다(저장 횟수로 판정).

설계와 다른 점:

- **붙었는지 확인은 `ABOUT` 장벽** — `yxquerydatabaseone` 은 기록이 없을 때의 답 꼴이 확실하지 않고, 이전 질의의 `DONE` 과 섞일 수 있다.
- **새 설치에도 «내 DB» 항목을 만들어 붙인다** — 붙은 항목이 없을 때 템플릿 `url = "rapfi.db"` 로 띄우면 엔진이 `engine/rapfi.db` 를 새로 만들고, 이관은 이미 끝나 그 파일은 고아가 된다.
- **충돌 뒤엔 엔진이 쥔 사본이 새 항목(`(이 기기)`)의 것이 된다** — 표지 · 붙은 기록이 새 id 로 옮겨 가, 다음 되쓰기가 또 충돌 사본을 만들지 않는다. 원래 항목은 스테이징 없이 남고 다시 붙이면 새로 복사한다.
- **폴더 쪽 저널도 스테이징에 함께 복사하고 `baseJournal` 로 지문을 둔다** — PC 가 본 파일은 그대로 두고 저널만 덧붙인 변화도 충돌로 잡는다(저널을 지우는 `dropJournal` 이 그 변화를 덮지 않게).
- **엔진이 이미 내려간 사본은 접지 않고 본 파일 + 저널을 그대로** 보낸다(저널 짝은 웹 · 데스크톱 · 엔진이 모두 읽는다). 저널 쓰기만 실패하면 본 파일 지문을 `base` 로 적고 dirty 를 남겨, 다음 시도가 자기 파일을 «PC 변경»으로 오해하지 않게 했다.
- **ON_STOP 되쓰기는 엔진이 떠 있을 때만**, 엔진이 내려간 뒤의 되쓰기(엔진 끄기 · 유휴 정리)는 3.5초 기다린 뒤(닫을 때의 저장이 끝나게) 보통 우선순위로 — `disconnect()` 가 `EngineService` 를 바로 멈추므로 표지가 붙들 수 없다. 끊기면 dirty 가 남아 다음 기동에 이어 간다.
- **스테이징 사본은 항목마다 남긴다**(다시 붙일 때 복사 생략). 휴지통 · 빼기 때의 `dropStaging` 은 화면이 붙는 L5-6 에서.
- `LibraryRepository.recordSaved`(앱 저장소 항목의 지문 갱신)는 L5-6 저장소의 몫 — 지금은 다음 맞추기가 크기 · 시각으로 알아채 지문을 다시 잰다.

### 실기 (2026-11-28 — Galaxy A16 · Android 17, debug `ce89992` → 고친 뒤 `90c0b1f`)

표본은 잔월 연구 DB(79MB · 817만 국면)의 사본. 정식 앱은 건드리지 않았다(debug 가 따로 깔림).

확인한 것:

- 첫 화면 · 상세: 새 설치 «내 DB» 붙음 · 가져오기(DocumentsUI) 79MB 약 3초 + 두 번 세기 약 20초(D5 807만 / 미분류 9.9만, 뿌리) · 자동 커버가 주형 색 ·
  주형 줄 → 세 돌 · 뿌리 열기 + «두던 판으로 돌아가기» · 커버 시트(일식 다시 누르면 무늬, 사이드카 저장) · 붙인 채 이름 바꾸기 · 휴지통 · 되돌리기 · 새 DB · 아주 지우기 · 탭 이동에도 상세 스택 유지.
- 열기: 엔진 전환 순서(`INFO usedatabase 0` → `YXSETDATABASE` → `ABOUT`), 817만 레코드 3.8초 적재, 열린 DB 로 조회. 폴더 항목은 스테이징 복사 뒤 약 9 ~ 12초(접기 + 적재).
- 폴더(SAF): Download 뿌리는 시스템이 막고 하위 폴더는 됨 · 사이드카가 웹과 같은 꼴 · 폴더 항목 세기 · 저널 동행 되쓰기(본체 + 저널, base 갱신) ·
  **충돌 사본**(폴더 파일을 바꿔 둔 채 되쓰기 → 원본 그대로, `zan12 (이 기기).db` + 저널, 새 항목이 붙음) · 이름 + «파일 이름도 같이 바꾸기»(저널도 같이) ·
  «라이브러리에서 빼기»(붙은 폴더는 거절 문구, 다른 DB 연 뒤 빼면 칩 사라지고 스테이징 · `_bak1` 정리, 폴더 파일은 그대로).

고친 것(`90c0b1f`, 폰에서 다시 확인):

- 상세 [지우기] 뒤 보드 탭으로 튐 — `LibraryEvent.Back` 과 항목이 사라진 상세가 두 번 pop. 상세 onBack 을 자기 백스택 항목일 때만.
- 홈으로 나가도 dirty 폴더 사본이 안 감 — 같은 ON_STOP 의 유휴 저장 끝이 검사보다 늦고 플래그만 봤다. `onBackground` 에서 지문을 지금 잰다.
- 빈 판 시작으로 열 때 «시작 국면(0수)으로» → «빈 판에서 시작».

본 것(고치지 않음 — 정할 일):

- **주형 분류가 레코드 몇 개로 무너진다**: 폰에서 몇 수 탐색해 레코드 7개가 늘자 분류 807만 → 3(I9 3돌 국면 하나가 생겨, «모든 부모가 같아야» 규칙이
  미분류를 자손 전체로 번지게 함). 웹 `yxdbindex` 로 같은 파일을 세도 같다 — 앱 · 웹 공통 알고리즘(§5)의 성질.
- 앱이 cached(adj 900, 포그라운드 서비스 없음)인 동안 엔진이 5분에 CPU 353초를 써 시스템(phantom process killer)이 앱째 죽인 일이 한 번(15:19). 무엇이 돌던 중이었는지는 확인하지 못했다.
- «아주 지우기»는 묻지 않고 지운다. [+ 추가] FAB 의 이름이 접근성 트리에 안 보인다.
- 색인 없이 마친 항목(`ScanNote.MEMORY`)엔 «다시 세기»가 없다 — 메모리가 아니라 시스템 kill 로 그리 됐어도 다시 셀 길이 없다.
- 붙은 동안 엔진의 압축 백업 `<key>_bak1.db`(본체 크기)가 스테이징에 남는다 — 빼기 · 지우기 때 정리.
- 상세를 연 채 가로로 돌리면 상세 단독 화면 그대로(두 칸은 첫 화면에서만). 새 APK 설치 직후 첫 기동에 «엔진 오류»가 잠깐 — 다시 재현되지 않음. 충돌 알림 줄은 못 봤다.

확인하지 못한 것:

- 저메모리 에뮬레이터 · 이관 뒤 첫 기동(정식 앱 위에 옛 빌드를 깔아야 해서 묻기로) · 폴더 권한 잃음 / «폴더 다시 허용» · 작업 알림 [취소] ·
  옮기기와 복사 취소(4초라 못 누름) · 옛 `connect` 백 스택 복원 · 엔진 탐색이 실제로 저널을 늘린 경우의 ON_STOP(초반 국면은 이미 DB 에 있어 안 늘었다 — 저널을 손으로 바꿔 경로를 확인).
