## 1. 진단 요약

### DB 값이 안 보이고 엔진이 DB 를 안 쓰는 것처럼 보임 — 프로토콜 버그 아님

- 엔진은 DB 를 쓴다(`EVAL +M151` 12초 안). `YXSETDATABASE` · `usedatabase` 순서 정상.
- 표본 DB 의 내용은 5수부터. 그 앞 칸들은 Rapfi 가 **조회하면서 남긴 LABEL_NONE 레코드**(빵 부스러기)라
  `displayLabel` 이 비어 `DbCell.display` → `BoardUiMapper.dbLabelsOf` 에서 빠진다. 데스크톱 Yixin 은 같은 칸에 DB 칸 그림(태그만 있어도)을 그린다.
- 분석 중에는 `setPosition` 이 칸을 비우고 `refresh()` 가 `Thinking` 이라 미뤄져, 검색이 끝나(Ready) 다시 물을 때까지 비어 있다 → **3번**.

### «이 DB 열기»가 빈 판으로 감

- 가장 큰 뿌리가 빵 부스러기 때문에 «빈 판 · 아래 809만» → **1번**.

### 5번 — 주형 분류 무너짐(807만 → 3)

- Phone Copy 에서 5돌 연구 국면 B[F9 H8 H7] W[H9 J9] 에 대칭 동치 부모 B[G8 H8] W[I10 I8] 가 하나 더 생겼고,
  그 부모의 DB 부모는 비표준 3돌 B[G8 H8] W[I10] 뿐 → 미분류(26) → «n > 3 이면 모든 부모의 주형이 같아야» 규칙이 자손 807만 전체로 번짐.
- 앱 `YxdbIndex.kt` · 웹 `yxdbindex.ts` 공통 알고리즘의 성질.

### 6번 — 백그라운드 CPU 353초로 앱째 죽음

- exit-info: `Caused by child process: excessive cpu 353240 during 300104 dur=16721 limit=25` (cached 앱 CPU 검사).
- logcat: EngineService 가 시작 5ms 뒤 멈춤(17:23:16.816 → .821) — 엔진이 붙어 있는데 서비스가 없다.
- 원인: `open()` 이 `EngineService.start` 뒤 `transportFor()` → `bootPath()` 에서 멈추는 사이 상태는 아직 `Disconnected`,
  서비스는 «Disconnected 면 stopSelf» 라 바로 멈춤. L5-4 `a8605b7` 에서 들어옴. 정식 0.16.0(2026-11-01)은 해당 없음.

## 2. P1 — 6 · 3 · 7

### 6. 백그라운드 CPU

- 6a `EngineRepository.sessionWanted`(connect ~ disconnect) — 서비스는 `!wanted && !Thinking && !reconnecting && !held` 일 때만 멈춘다.
- 6b `open()` 에서 `transportFor(target)` 을 서비스 시작 **앞**으로.
- 6c 앱을 떠난 뒤 분석 자동 정지: `UiPrefs.backgroundAnalysisStopMin`(`engine.bgstop.min`, 기본 30, 0=끔) ·
  설정 ▸ 엔진 칩 «앱을 떠난 뒤 분석 정지» · `EngineIdleWatcher` 가 `EngineIdlePolicy.backgroundStopAfterMs` 로 기다렸다 `engine.stop()`.
  `EngineRepository.analysisRunning` 은 `analyze()` 의 검색만(대국 수 · 검토 · 증명은 자르지 않음).
- 6d 시험: 느린 `bootPath` 에도 서비스가 foreground 로 남는지(Robolectric) — **미완**.
- 웹: 해당 없음(브라우저 워커).
- 남은 위험(범위 밖): `LocalEngineTransport` 닫을 때 `destroyForcibly` 3초 유예.

### 3. 분석 중 수를 두면 멈춤 → DB 질의 → 다시 검색

- `AnalyzeParams.beforeSearch` — `analyze()` 안 `awaitIdle()` 뒤, `YxBoard` 앞에서 실행.
- `DatabaseRepository.refreshBetweenSearches()` — `Thinking` 검사 없이 질의(짝 맞추기 등록).
- `BoardViewModel.startAnalysis` 가 검색을 넘겨받을 때만 훅을 단다.
- 시험: VM 시험(넘겨받을 때만 훅) 완료. 엔진 저장소 수준 순서 시험(yxstop → 질의 → yxboard → yxnbest) **미완**.
- 웹: `boardDb.ts` 가 이미 분석 중 질의(워커가 검색을 양보) — 확인만.

### 7. «완전 삭제» · «다시 세기»

## 3. P2 — 5 · 1의 색인 (웹 먼저 → 안드로이드)

웹이 먼저 또는 같이 나가야 한다 — 아니면 섞인 규칙 DB 를 두 앱이 번갈아 다시 센다.

- 5 분류: 26 = 비표준(NONSTD) — **표를 던지지 않음**(중립). 27 = 진짜 엇갈림(MIXED) — 자손으로 번짐.
  info 필드 비트 0–7(0xFF = 아직)이라 27 이 들어간다. 사이드카에는 27 을 26 칸에 접어 넣고, `ClassifiedFn` · 분리 매핑도 27 → 26.
- `INDEX_VERSION = 3`, `current` 는 `indexVersion >= 3`(웹 `statsCurrent` · 앱 `DbStats.current` 둘 다).
- 1 시작 국면: 부분트리 크기를 센 뒤 `parent` 배열을 층별로 훑어, 가장 큰 뿌리에서 가장 무거운 자식(첫 부모 기준 부분트리)이
  90% 이상인 동안 내려간다. `DbRoot.start`(hex, 선택)로 저장.
- 웹: `src/core/database/yxdbindex.ts`(UNCLASSIFIED 157, 규칙 360–366) · `yxdbstats.ts` · `features/library/libraryStore.ts` `startMovesOf`.
  안드로이드: `YxdbIndex.kt` · `DbStats` · 분리 매핑.
- 시험: 무너짐 재현(Phone Copy 꼴의 작은 합성 DB) · l5 교차 골든(웹 ↔ 앱 같은 수) · 버전 올림 뒤 다시 세기 한 번.

## 4. P3 — 화면 (안드로이드 + 웹)

- 1 설정 «DB 열 때 시작 국면»: 갈라지는 곳(기본) / 가장 큰 뿌리 / 빈 판. 상세에 «기록 시작점» · «n수 국면에서 엽니다» + 미니 판.
